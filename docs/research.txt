Your requirements point toward a small macro facility, not a Rust-sized macro subsystem:

Macro invocation already has a distinctive syntax: u_name<.
Macros are dyadic/monadic like X_eTaL functions; left/right arguments are normally source strings.
They should demonstrate the “eXtensible” part of X_eTaL.
Users need to define their own macros in X_eTaL, not Rust.
Native/C-ABI extensions are another extension mechanism, but should compose naturally with macros.
You explicitly do not want dozens of built-in macros or a complicated macro language.

I think that leads to a surprisingly small design: perhaps 4–6 built-in macros, .xtlm macro libraries, and ordinary X_eTaL functions as the macro implementation language.

Macro ranking

I would start with this set:

Rank	Macro	Example	Purpose	Add?
1	u_se<	"c:" u_se< "Combinators"	import/use library	Already
2	u_if<	"condition" u_if< "then ; else"	conditional source generation	Yes
3	u_for< / u_each<	"x : 1..10" u_for< "..."	generate repeated expressions/definitions	Probably
4	u_native<	"math" u_native< "libm.so"	expose native extension library	Yes, eventually
5	u_include<	u_include< "foo.xtl"	textual/source inclusion	Maybe
6	u_assert<	"condition" u_assert< "message"	compile-time assertion	Maybe
—	u_eval<	u_eval< "expression"	explicit compile-time evaluation	Avoid initially
—	u_quote<	...	manipulate syntax/AST	Avoid initially

The key criterion is:

A macro should do something that an ordinary X_eTaL function cannot naturally do because it needs to happen before normal evaluation.

That keeps the namespace meaningful.

1. u_if< — highest-value new macro

This immediately demonstrates language extension rather than merely library loading.

Conceptually:

"FEATURE_GPU" u_if< "gpu_version ; cpu_version"

or perhaps:

"rank = 2" u_if< "matrix_code ; general_code"

It is useful for conditional definitions, specialization, platform-dependent code, and generated demonstrations.

Most importantly, it gives you an immediate reason macros exist: it chooses which X_eTaL source gets compiled.

2. u_each< or u_for< — source generation

Array languages don't usually need runtime loops, so I prefer u_each< over u_for< if this really means compile-time expansion:

"A B C" u_each< "_r := ..."

This can generate families of definitions, tests, wrappers, etc.

But I'd be careful here. If ordinary array operations solve the use case, it belongs in ordinary X_eTaL. The compelling case is generating definitions, not calculating arrays.

3. Native library loading

I like the concept but would separate loading a native module from calling a native function.

For example:

"m:" u_native< "./libmath.so"

could establish namespace m: from a native library.

Then:

m:sin 1.5

should ideally look like an ordinary X_eTaL function call.

I would not make every foreign call look like:

[]SVO ...

because FFI is an implementation boundary, not something the application programmer should continually see.

More on that below.

4. u_include<

Potentially:

u_include< "generated.xtl"

This is useful, but u_se< may already make it redundant. I'd only add it if there's a real semantic distinction:

u_se< = import compiled/module namespace
u_include< = insert source here

Otherwise one mechanism is better.

5. u_assert<

Compile-time assertions are especially useful once macros themselves generate programs:

"rank _r = 2" u_assert< "matrix required"

The important distinction would be compile-time versus ordinary runtime assertion.

Useful, but not needed for the first extensibility demo.

The interesting part: user-defined macros

I strongly favor your .xtlm idea.

Specifically:

.xtlm = X_eTaL Macro Library

I prefer .xtlm to .mxtl because it reads as an extension of the existing format:

foo.xtl     X_eTaL source/library
foo.xtlm    X_eTaL macro library

And I would avoid inventing a special macro-definition grammar.

Instead, the file type changes the interpretation of its functions.

Suppose strings.xtlm contains conceptually:

_l _mymacro _r := ...

In a normal .xtl:

_mymacro

defines an ordinary X_eTaL function.

In an .xtlm:

_mymacro

defines a macro whose:

_l = raw left source string
_r = raw right source string

and whose result is:

String containing X_eTaL source

That source goes back through the parser/compiler.

So:

"my left arg" u:mymacro< "my right arg"

becomes approximately:

source =
    macro_library["u:mymacro"](
        "my left arg",
        "my right arg"
    )

AST = parse(source)

That's wonderfully small.

Why I like this better than macro-definition syntax

You don't need:

macro ...
endmacro

or:

u_macro< ...

or Rust-like:

macro_rules!

You already have a programming language.

Use it.

Rust's declarative macros have a separate matcher/transcriber language, while procedural macros effectively operate as functions transforming syntax. X_eTaL can take the simpler route because your macro contract is intentionally narrower:

(String, String) -> String

That's closer to a tiny compile-time function system than Rust's general token-tree machinery.

A concrete example

Suppose you want a simple unless macro.

control.xtlm:

_l _unless _r := ...

where _l is the condition source and _r is the expression source.

Then:

"x = 0" c:unless< "42"

might expand into whatever actual X_eTaL conditional expression corresponds to:

not (x = 0) ... 42

The macro implementation itself is ordinary string-processing X_eTaL.

That demonstrates something significant:

X_eTaL source
      |
      v
macro invocation
      |
      v
X_eTaL macro function
(String, String) -> String
      |
      v
generated X_eTaL source
      |
      v
normal parser/type checker
      |
      v
normal X_eTaL program

That's enough to legitimately call the language extensible.

Compile .xtlm first

I would indeed make macro libraries compile before the .xtl that uses them.

That gives a clean phase distinction:

                 X_eTaL compilation

       .xtlm
         |
         v
   macro compiler
         |
         v
   macro library
         |
         +------------------+
                            |
                            v
.xtl ---> lexical scan ---> macro expansion
                            |
                            v
                         parser
                            |
                            v
                       type checker
                            |
                            v
                        evaluator

This is conceptually similar to why Rust macros are brought into scope before use, although Rust has substantially more complicated macro scoping and expansion rules.

And it avoids the nasty question:

Can a macro define the macro that expands the rest of the file containing its own definition?

For V1: no.

.xtlm is compiled first. .xtl consumes the resulting macro environment.

Much easier to reason about.

One restriction I would impose immediately

Macro expansion is recursive, but bounded.

For example:

MAX_MACRO_EXPANSION_DEPTH = 32

because:

_a< -> "_b< ..."
_b< -> "_a< ..."

otherwise gives you an entertaining compiler heater.

Also provide:

xetal --expand foo.xtl

which prints the source after macro expansion.

That is probably more important than adding another built-in macro.

Even better:

xetal --expand-macro foo.xtl:17

showing:

before:
    "x" u:foo< "y"

expands to:
    ...

defined:
    macros/foo.xtlm:23

For a teaching language, macro expansion should be extremely visible.

I would not implement Lisp-style macros yet

Lisp macros are extraordinarily powerful because they're manipulating the language's own natural representation of programs.

X_eTaL doesn't have Lisp's homoiconicity.

Trying to recreate that now leads toward:

AST values
quote
unquote
splice
hygiene
gensym
macro scopes
syntax objects
source locations

That's exactly the overengineering you're trying to avoid.

Your String→String mechanism gets you most of the pedagogical payoff:

A user can add something that looks like new X_eTaL syntax.

Later you could introduce:

Syntax -> Syntax

without invalidating .xtlm.

Rust itself illustrates why stopping early is attractive: it has declarative macros plus three forms of procedural macro, operating on token streams, with substantial rules around scope and hygiene. X_eTaL doesn't need that complexity to prove extensibility.

C ABI: make this the second extension axis

I'd describe the architecture as:

                 X_eTaL EXTENSIBILITY

            syntax                 capability
              |                        |
              v                        v
          .xtlm macros             native ABI
              |                        |
       String -> String          X_eTaL -> C ABI
              |                        |
              +-----------+------------+
                          |
                          v
                       X_eTaL

They solve different problems.

Macros extend what programs can say.

Native libraries extend what programs can do.

That's a nice distinction.

[]SVO could be the low-level mechanism

I think your []SVO idea is reasonable if it is the primitive, rather than the normal user interface.

Something approximately like:

[]SVO "libm.so" "cos" "f64(f64)"

could return a callable function, or bind one.

But I'd probably make the interface slightly more structured if X_eTaL types permit it:

f := []SVO "libm.so" ("cos" ; "f64" ; "f64")

Then:

f 1.2

The exact syntax is secondary to the architecture:

[]SVO
  |
  +-- load dynamic library
  +-- resolve symbol
  +-- validate ABI signature
  +-- construct X_eTaL callable

Then an ordinary .xtl library hides this:

Math.xtl
    |
    +-- cos := []SVO ...
    +-- sin := []SVO ...
    +-- sqrt := []SVO ...

Application:

"m:" u_se< "Math"

m:cos 1.2

Now the user doesn't care whether m:cos is:

interpreted X_eTaL,
compiled X_eTaL,
Rust,
C,
Fortran,
BLAS,
CUDA,
an FPGA driver,

provided it satisfies the declared X_eTaL type.

That is much more powerful than making u_native< the calling convention.

Macros + native libraries become particularly interesting

The two extension mechanisms can compose.

Suppose somebody ships:

blas.xtlm
libxetal_blas.so

The macro library can generate bindings/specializations:

"f32[_,_]" blas:gemm< "A B"

which expands to ordinary X_eTaL referencing functions supplied by the native library.

Or an ML extension could have:

"Conv2D" ml:layer< "3 32 3 3"

expand into ordinary typed X_eTaL which ultimately calls optimized native kernels.

Now eXtensible means something substantive rather than merely being part of the acronym.

What I would actually implement

I would keep the first milestone deliberately tiny:

Keep u_se<.
Add .xtlm.
In .xtlm, ordinary-looking X_eTaL function definitions define macros with the contract (String, String) -> String.
Add namespace import of macro libraries, so u: in u:mymacro< identifies the macro library namespace.
Add --expand and a hard macro-expansion-depth limit.
Implement one standard .xtlm library containing u_if< and perhaps u_each<, rather than hard-coding them in Rust.
Later add []SVO as the primitive native-symbol operation, and hide it behind ordinary .xtl libraries.

There is an appealing bootstrap story here:

                 built into compiler
                        |
                      u_se<
                        |
          +-------------+-------------+
          |                           |
        .xtl                        .xtlm
          |                           |
    X_eTaL libraries            macro libraries
          |                           |
          |                    user-defined u_foo<
          |                           |
          +-------------+-------------+
                        |
                      X_eTaL
                        |
                      []SVO
                        |
                  native libraries

And I would stop there until concrete programs demonstrate something missing.

The result is unusually economical: one built-in macro mechanism, one macro-library file type, ordinary X_eTaL as the macro implementation language, and one FFI primitive. You get Lisp-like language extensibility as a user-facing idea, Rust-like obvious macro invocation syntax, and C/Rust-like native extension capability, without inheriting the complexity of any of those macro systems.

One naming tweak I particularly like: reserve u_ for compiler/built-in macros (u_se<, perhaps u_if<) while imported macro libraries naturally use their namespace (c:...<, ml:...<, test:...<). That makes the distinction between the tiny language core and user-created language extensions visible directly in source.
